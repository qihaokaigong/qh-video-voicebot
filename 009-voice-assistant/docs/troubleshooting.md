# 故障排查

先记录屏幕最后显示的状态、操作发生在按下还是松开按钮之后、是否听到声音，以及 Agent 工具返回的
结构化错误。不要把 API Key、Wi-Fi 密码、完整配置载荷或包含它们的串口日志发到 Issue。

## 屏幕完全黑屏

这不是网络或 API Key 问题。优先检查供电、共地、GMT130-V1.0/ST7789 型号、GPIO9/10/11/12、
SPI mode 3 和硬件 Profile 是否完全一致。曾经出现过固件能运行但屏幕初始化参数不匹配的情况；
因此不能仅凭串口工作就继续配置。黑屏必须先修复。

## 屏幕一直显示“等待配置”

表示固件已启动，但没有可激活的设备配置。保持 USB 连接，让 Agent 使用 Skill 的 `configure`
流程打开本地中文页面。不要安装 Voice Gateway，也不要把配置写进源码重新编译。

## 配置后显示“错误，请稍后重试”

按层次检查：

1. Wi-Fi 是否为 2.4 GHz、名称和密码是否正确；
2. 时间同步是否完成；TLS 在设备时间错误时会失败；
3. 是否开通“豆包实时语音模型 3.0（Seeduplex）”；
4. 是否使用“API Key 管理”中的 Key，而不是 APP ID、Access Token 或 AK/SK；
5. 音色 ID 是否属于当前模型和项目；
6. Provider 返回的错误码和 WebSocket 断开阶段。

只重新填写出错层所需配置，不要在 Agent 对话中粘贴 Key。

## 按住说话正常，松开后回答报错

这通常说明麦克风和按钮已经工作，问题位于输入提交、Provider 回复事件、下行帧大小或播放启动。
曾经的实机问题包括 WebSocket 客户端接收帧上限过小：已经收到回答文本，但后续较大的音频帧在进入
应用解析前断开。应保留断开码、最后事件类型和失败阶段，再由 Agent 对照当前固件测试定位，不能简单
归因于“模型没有回答”。

## 有回答，但声音断断续续或杂音明显

实时接口分片返回音频是正常的，问题不在“分片”本身，而在设备是否把网络抖动直接暴露给 I²S。
当前修复采用有界 PCM 缓冲、达到预缓冲阈值后连续播放，并在 Provider 完成后继续排空尾部数据。

依次检查：

- 下行确实是 24 kHz、signed 16-bit、little-endian、单声道 PCM；
- Base64 解码后字节数为偶数，没有把 JSON 文本或压缩音频当 PCM；
- 播放缓冲没有频繁下溢；
- `response.done` 没有立即停止仍在缓冲中的音频；
- I²S BCLK/LRC/DIN 和供电、共地、扬声器功率匹配；
- 软件音量没有造成削波。

不要通过无限增大缓冲掩盖问题；缓冲过大会显著增加回复延迟。

## 屏幕正常、回答完整，但没有上传到 QH

QH 同步是可选的结构化事件通道，不参与当前语音闭环。先确认本次本地对话已经完成，再单独检查 QH
配置、网络响应和重试结果。不要为了恢复 QH 同步把 Provider Key 或原始音频发送到平台。

## 重启后又要求配置

检查配置事务是否收到设备确认、NVS 双槽激活是否成功，以及 Flash 是否执行了全擦除。正常稳定烧录
的 Manifest 必须声明 `eraseAll: false`；重新烧录不应无故清除用户配置区域。

## 仍无法定位

让 Agent 按 `qh-voice-skill` 的分层检查收集以下非敏感信息：主机类型、串口、Release ID、Profile ID、
固件哈希、屏幕状态、失败阶段、Provider 错误码和断开码。把“已经实测的现象”和“尚未执行的建议”
分开记录，再决定是否需要修改代码。
